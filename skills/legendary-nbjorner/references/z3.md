# Worked instantiation: Z3

Use this reference when applying the skill inside `Z3Prover/z3`. It preserves
the Z3-specific commands, paths, and macros checked for the original skill
against Z3 `master` at `a200baf4416121d396ed5e1f63aa7005d2658715`
(2026-10-21), and z3test as of that date. This is a worked instantiation,
not a layout to assume for other tools. Recheck it against your checkout.

## Build and setup

Requires a local Z3 checkout, a C++ toolchain, CMake, and Ninja for these
examples. Regression testing also uses a checkout of `Z3Prover/z3test` and
Python. Reuse existing build directories. Configuring and building writes
build files, takes several minutes, and can use significant CPU; keep the
build within the task's resource budget.

```sh
# Debug build: enables SASSERT checks and TRACE output.
cmake -G Ninja -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel

# Release build with tracing, for performance work that still needs traces.
cmake -G Ninja -S . -B build-rel -DCMAKE_BUILD_TYPE=Release -DZ3_ENABLE_TRACING_FOR_NON_DEBUG=ON

# Unit tests.
cmake --build build --target test-z3 --parallel
./build/test-z3 -a            # all tests in FOR_EACH_ALL_TEST
./build/test-z3 <name>        # one test, e.g. ./build/test-z3 totalizer
```

The release command configures `build-rel`; build that directory before
using its executable.

Regression tests live in the separate `Z3Prover/z3test` repository. Look
for an existing local checkout first. If there is none, tell the user that
z3test regressions were skipped and ask before cloning it, since that uses
the network. Check the license of anything copied from it. From the Z3
checkout, with z3test alongside `build/`:

```sh
python z3test/scripts/test_benchmarks.py ./build/z3 z3test/regressions/smt2
```

`test_benchmarks.py` runs each `<name>.smt2` with `model_validate=true` and
requires the output to match `<name>.expected.out` exactly. Files renamed to
`.smt2.disabled` are skipped. This behavior was checked in z3test's
`scripts/util.py` and `regressions/smt2` as recorded in the provenance;
z3test was not pinned to a commit.

## Localizing a Z3 failure

Typical areas are parsing and `cmd_context`, preprocessing
(`ast/simplifiers`, `tactic`), rewriting (`ast/rewriter`), solving (`smt`,
`sat/smt`, `math/lp`, `nlsat`, `opt`), model construction (model converters),
and the API. These areas interact; treat the list as a map rather than a
fixed execution order.

Useful `z3` switches:

- `-tr:<tag>`: trace a tag; requires a debug or tracing build.
- `-v:<n>`: verbosity.
- `-st`: statistics.
- `-T:<seconds>`: timeout.
- `param=value`: parameters such as `model_validate=true` or
  `smt.arith.solver=6`.

Use supported parameters to turn preprocessing steps off when localizing a
failure, and validate models with `model_validate=true`. Add
`TRACE(tag, tout << ...)` where state is unclear. New tags must be declared
in `src/util/trace_tags.def`. Remove ad-hoc `std::cout` debugging afterward.

When a simplifier eliminates or replaces variables, register the change with
the model converter so the final model satisfies the original input.
Parameters for heuristics are declared in `.pyg` parameter files.
Unsupported constructs can be rejected with `default_exception`, which
surfaces as an error or `unknown`; follow the component's existing contract.
Do not translate cancellation or resource exceptions into `sat` or `unsat`.
For crashes, reproduce in a debug build and record the `SASSERT` location.

## Recording Z3 regressions

For issue-driven fixes, add `regressions/smt2/<issue>.smt2` and
`<issue>.expected.out` in z3test. Expected output can be generated from the
fixed build, but must then be read and checked for correctness, not accepted
because that build printed it. Use `.smt2.disabled` only for a known failure
tracked in an issue. Avoid timing-dependent or uncontrolled seed-dependent
outcomes.

For internal components that SMT-LIB cannot reach directly, the convention
is `src/test/<name>.cpp` defining `void tst_<name>()`, listed in
`src/test/CMakeLists.txt` and registered as `X(<name>)` in
`FOR_EACH_ALL_TEST` in `src/test/main.cpp`. Many existing tests are exploratory
drivers that print results. Prefer `ENSURE(...)` or `VERIFY(...)`, which
also fail in release builds, over output that nobody compares.

Run the relevant unit tests, `test-z3 -a`, and affected z3test directories as
appropriate to the task and project requirements. Report what ran, what
passed, and what was skipped. Model validation does not establish that an
`unsat` answer is correct. External checkers remain optional and follow the
availability and reporting rules in SKILL.md ("Optional external checks").

## Example: a model reconstruction regression

A reported QF_LIA issue returns `sat`, but model validation fails:

```sh
./build/z3 model_validate=true issue.smt2
```

Minimize while the invalid model persists. Disable preprocessing steps through
their parameters to narrow the failure, then trace the responsible
simplifier. If it eliminated a variable without model-converter registration,
add that registration. Record `regressions/smt2/NNNN.smt2` and reviewed
`NNNN.expected.out` in z3test, then run `test_benchmarks.py` on the affected
directory. This illustrates a possible repair, not the diagnosis for every
invalid model.
